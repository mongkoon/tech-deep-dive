# JavaScript의 동적 설계 역사와 ES6 `class` 도입 배경

## Q1. 사용 순간 선언되어 버리는 기능은 JavaScript 탄생 때부터 있었는가?

네, **1995년 JavaScript가 처음 세상에 나왔을 때부터 가지고 있던 가장 근본적인 특징**입니다. 모든 객체를 '언제든 키(Key)와 값(Value)을 넣고 뺄 수 있는 동적 딕셔너리(해시맵)' 구조로 설계했기 때문입니다.

* **1995년 (최초 설계)**: `class` 문법 없이 생성자 함수와 `new`를 사용했으며, `this.countText = ...` 대입 순간 빈 객체(`this`)에 프로퍼티가 즉시 생성되었습니다.
* **2009년 (ES5 엄격 모드)**: `var` 없이 일반 변수를 선언할 때 전역 객체(`window`)에 자동 등록되던 버그는 `'use strict'` 도입으로 금지되었지만, 특정 객체(`this`)에 프로퍼티를 동적 추가하는 기능은 유지되었습니다.
* **2015년 (ES6 `class` 도입 후)**: 내부적으로는 여전히 프로토타입 기반으로 동작하므로 동적 프로퍼티 생성 규칙이 그대로 이어졌습니다.
* **현대 제어 수단**: `Object.seal()`, `Object.freeze()`, 또는 ES2022 `#` private 필드를 통해 동적 추가를 차단할 수 있습니다.

## Q2. JavaScript에 왜 `class`가 도입되었고, 왜 20년이나 늦게 도입되었나?

### 도입 이유
1. **난해한 상속 구현과 생태계 파편화 해소**: `Object.create(Parent.prototype)` 등 복잡한 반복 코드를 표준화하고 라이브러리별로 파편화된 헬퍼 문법을 통일하기 위함입니다.
2. **웹 애플리케이션 대형화와 OOP 개발자 유입**: SPA 시대가 열리며 Java·C#·C++ 출신 개발자들의 직관적인 `class`, `extends`, `super` 문법 요구가 커졌습니다.
3. **내장 객체(Built-in) 상속 한계 극복**: `Error`, `Array` 등 기본 내장 객체의 서브클래싱을 언어 차원에서 지원하기 위해 필요했습니다.

### 20년이나 늦게(2015년) 도입된 이유
1. **1995년 탄생 당시의 역할 분담**: 체계적인 OOP는 Java(애플릿)가, 가벼운 DOM 조작은 JavaScript가 맡는 보조 스크립트 언어로 출발했습니다.
2. **1999~2008년 'ES4'의 좌초**: 너무 거대한 기능을 한 번에 도입하려다 표준화 위원회(TC39) 내부 진영 간 충돌로 ES4가 폐기되면서 약 10년간 표준화가 정체되었습니다.
3. **프로토타입 순수주의자들의 반대**: 프로토타입 기반 언어에 `class` 문법을 씌우면 내부 동작에 대한 오해를 부른다는 커뮤니티 반대가 컸습니다.
